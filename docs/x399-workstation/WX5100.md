## Client buffers and asynchronous DMA

The native driver now owns a VRAM page allocator and persistent SDMA executor.
The first 64 MiB is reserved for firmware scanout and kernel rings/workspaces;
ATOM reservations and active cursors are also excluded. Buffer allocations
currently use the 256 MiB CPU aperture and are limited to 64 MiB each. The
allocator handles 64-bit VRAM offsets. At this checkpoint there were no
system-memory mappings; the next section records their implementation.
VRAM allocations outside the CPU aperture still need implementation.

Each open file has its own handles, monotonically increasing fences and
accounting. Client commands specify handles and bounded offsets; the kernel
constructs copy/fill packets and GPU addresses. A kernel worker executes jobs
in submission order, splitting large operations into SDMA packets. There are
at most 64 pending jobs per client and 256 for the device. Firmware startup is
root-only; ordinary clients can allocate, map, submit and wait afterwards.
Inherited file descriptors cannot issue commands from another team.

Mappings expose only that buffer, not the kernel command ring or registers.
Free/close revokes mappings and clones before VRAM reuse. Jobs retain buffer
and client references until completion, so closing a file cannot free memory
still in use by the GPU. A GPU failure stops new work and preserves affected
VRAM allocations until a cold boot. Hardware reset/recovery is not yet
implemented or qualified; this fault path is not a recovery claim.

## System RAM and GPU page tables

The driver now sets up a 1 GiB flat GART in private VMID0, backed by a 2 MiB
VRAM page table at offset 16 MiB. GPU addresses `0x10000000..0x4fffffff`
translate to wired Haiku RAM pages. `AMDGPU_CREATE_SYSTEM_BUFFER` creates
system-memory BOs using the existing ownership, mapping, submission and fence
API. Each 4 KiB PTE is validated against VI's 40-bit physical-address limit
and is snooped, readable and writable, with execution disabled. The CPU
mapping remains cached. No userspace physical address or PTE is accepted.
The same copy/fill executor now supports both memory domains.

GART allocation accounting is separate from VRAM accounting. Completed jobs
release their references before RAM can be unmapped: the kernel clears PTEs,
flushes CPU page-table writes and invalidates the GPU TLB before returning
pages to Haiku. Mapping revocation or engine/translation failure retains the
RAM's kernel area and wiring until a cold boot. Deleting the area on a timeout
would incorrectly return pages to the OS. VM protection faults are checked
alongside SDMA completion, so a fence alone cannot hide a redirected fault.
This is a kernel DMA address space, **not** per-client shader GPUVM support.
There are no user-supplied command buffers yet.

## GFX8 command processor bring-up

A new root-only `AMDGPU_GFX_TEST` path parses CE/PFP/ME header 1.0 and RLC
header 2.0 images for GFX8. It validates code/jump-table bounds and all RLC
restoration-array ranges before hardware access. The SMU transfer preserves
its running scratch area and authenticates a four-entry table (load mask
`0x438`). GFX uses a private 1 MiB kernel allocation at VRAM offset 40 MiB
for its destination and fences. The first 128 KiB of GART now holds a
64 KiB ring followed by a 64 KiB indirect-command area, both wired, snooped
and reserved from client allocation.
Only those private command PTEs have execute permission; client RAM PTEs
remain non-executable. No arbitrary userspace command streams or addresses
are accepted. SDMA must be idle while initialization and the bounded test run.

## Owned H.264 client sessions

The driver now has `AMDGPU_VIDEO_CREATE`, `AMDGPU_VIDEO_DECODE` and
`AMDGPU_VIDEO_DESTROY`. An `O_RDWR` file belongs to its opening team and owns
one session; different files have independent contexts and reference memory.
Closing the file destroys the firmware session and frees its allocation after
completion. Hardware faults retain the affected VRAM allocation. At most 32
sessions can exist, below the firmware's 40-handle configuration. A per-file
busy flag prevents another thread from replacing a session while a decode
waits for queued DMA to finish.

The first valid create request starts SMC/SDMA through the existing installed
firmware loader, then loads the pinned UVD image automatically. Invalid
headers/configurations and read-only requests are rejected before startup.
The API accepts progressive eight-bit 4:2:0 H.264 metadata and copied Annex B
slice NALs only. It rejects supplied parameter-set NALs, invalid flag bits,
out-of-range syntax fields and oversized input; the first picture must be an
IDR. The kernel constructs all firmware messages and GPU commands. Clients
cannot map the private memory or provide GPU addresses, firmware messages or
programs. The present input limit is 4 MiB per picture, with a 160 MiB maximum
session allocation inside the CPU aperture; unsupported configurations or
memory pressure return errors for the future software fallback path.

Each session has its own message, feedback, scaling, 128 KiB firmware session
context, bitstream, DPB, H.264 context and linear NV12 output buffers. The DPB
and context sizes follow Mesa's Polaris H.264 PERF sizing. Four guard pages
bound the working buffers. Decodes synchronously check the hardware fence,
ring retirement, guards and both VM fault registers, then copy output into
the requesting process. The userspace metadata layer below supplies SPS/PPS
parsing, picture order and reference bookkeeping. Timestamped output queues
and the Media Kit adapter remain to be implemented.

### SDMA video readback to cached RAM

The next driver moves bulk video initialization, target clearing and output
readback off the per-word CPU VRAM path. Every video session owns a wired,
kernel-only cached RAM area, mapped by snooped, non-executable GART PTEs.
SDMA clears its private VRAM before use and each target before decode, then
copies the completed NV12 surface into that RAM. Userspace receives pixels
only after both the UVD and SDMA fences and idle checks. RAM guards and tail
padding are checked in addition to all four existing VRAM guards. Alternating
CPU fill patterns in the RAM destination expose stale or short copies to the
independent comparison.

The device mutex and `WaitDmaIdle` serialize these private operations with
queued client DMA. Healthy session destruction unbinds and releases the RAM
and VRAM allocations; a fault retains wired RAM and its GPU address range,

## Implementation and acceptance work remaining

1. **General graphics execution:** complete shader/resource isolation before
   exposing general copied/queued submission to unprivileged applications.
   Extend the qualified kernel/Mesa queue to reset/reuse and eviction/migration,
   and extend IRQ completion to other engines. Preserve the
   qualified VRAM/RAM ownership, isolation,
   zeroing and UVD paths; verify concurrent clients, teardown and timeouts.
2. **Display and desktop:** extend the read-only DCE snapshot to native
   DCE 11.2 modesetting, all attached displays, hardware cursor, retrace,
   hotplug and the fork's display layout/scaling API. Verify physical output,
   mode changes and repeated layouts while retaining framebuffer recovery.
   Accelerated 2D needs independent drawing comparisons.
3. **Mesa:** qualify and extend the private native AMD winsys backend.
   Evaluate RadeonSI and RADV/Zink against the fork's existing Haiku EGL and
   OpenGL Kit presentation paths. Require the AMD hardware renderer with no
   per-process environment, independent pixel readback, representative
   rendering tests, multiple windows, resizing/occlusion and sustained load.
   Keep software fallback functional when the device cannot initialize.
4. **Installed media and applications:** preserve the qualified H.264 and
   HEVC Main/Main-10 decoder and three-minute hardware playback in both
   private applications. Integrate the qualified addon and app selection into
   release defaults, then repeat file/MSE playback, paused seek, malformed
   input, startup/runtime fallback and sustained performance on the installed
   build. Physical audio/display latency remains unmeasured; CPU Mesa browser
   composition does not establish AMD graphics acceleration.
5. **Installed release:** assemble final driver, licensed firmware, Mesa,
   decoder and application packages; cross-build, QEMU smoke, commit and
   integrate, then install the complete build on X399 with a tested rollback.
   The regular core/media/devel packages and VM upgrade are already qualified;
   native full-release installation and verification remain. Reboot and rerun
   graphics, display, airTime and Summit checks on the installed defaults.
   The goal remains open until all of this works.

Immediate next work: qualify userspace command submission and fault containment,
followed by Mesa and native display. Engine timeout/reset
and reuse still need qualification. Mapped VRAM remains bounded by the CPU
aperture; device-only buffers now expose the remaining 7.75 GiB, and RAM BOs
use GART. SMC/SDMA startup now uses the installed firmware package
automatically; complete release-image integration remains open.

  reusable Haiku integration ideas, but its units implement GFX6 and DMA1,
  not the WX 5100's GFX8/SDMA3. It is not a ready-made Polaris driver.
- [RadeonHDunofficial](https://github.com/KevinAdams05/RadeonHDunofficial),
  inspected at `f5740845cc36d617901add10a60eae38a58aae84`, local
  `x399/src/RadeonHDunofficial`: MIT-licensed display/ATOM/PLL reference.
  Its README describes DCE 10–12 enablement as largely untested; its tested
  hardware table does not include this WX5100. No binaries from that fork
  are installed here. A separate driver must not co-own this driver's MMIO
  or VRAM allocations.
- Mesa in `src/forks/mesa`: the shared checkout belongs to other work too.
  AMD changes are isolated in `x399/mesa-wx5100`, branch `airos-wx5100`.
  The private native backend reuses existing Haiku EGL presentation; broad
  GPU and application qualification remains required.
- airTime `src/engine/HardwareVideoDecoder.cpp` explicitly enumerates
  supported hardware add-ons. Summit's corresponding Media Kit selection
  lives in WebKit `Source/WebCore/platform/graphics/haiku`; supporting a new
  Media Kit decoder alone does not establish both apps select it correctly.
