# RTL8188GU (RTL8710BU) and RTL8188FU Wi-Fi

`realtekwifi` (FreeBSD's `rtwn`) drives two more 2.4 GHz 802.11n USB dongle
chips:

- **RTL8188FU / RTL8188FTV** (`0bda:f179`): FreeBSD main's `rtl8188f` chip
  code, unchanged apart from one IQ calibration fix.
- **RTL8188GU**, which is an **RTL8710B** (Linux: RTL8710BU, `rtl8xxxu/
  8710b.c`), USB IDs `0bda:b711` and `0bda:2005` (TOTOLINK N150UA V5). The
  dongles first show a driver CD (`0bda:1a2b`), which `usb_modeswitch`
  ejects. This chip code is new: `dev/rtwn/rtl8710b`.

Status: **built blind, untested on hardware** (no such dongle in the lab).
It lives on branch `rtl8710b`, not on `master`.

## Licensing

`realtekwifi` stays under BSD/MIT licences. No BSD-licensed RTL8710B driver
exists (FreeBSD, OpenBSD, NetBSD, DragonFly have none); the only source of
its register tables is Linux's GPL-2.0-only `rtl8xxxu`. So:

- The chip code (`dev/rtwn/rtl8710b`, MIT or BSD-2-Clause) is written for
  rtwn from what the hardware needs; where it follows the behaviour of
  Linux's driver, comments name the Linux function. No Linux code is copied.
  Register addresses and the constants of the calibration and channel
  sequences are hardware facts and are in the code.
- The MAC, BB, AGC and RF initialisation tables (both package variants)
  are not in any BSD/MIT file and not in the `realtekwifi` binary. They are
  a GPL-2.0 data file, `firmware/realtekwifi/rtwn-rtl8710b-tables.bin`,
  loaded at run time through `firmware_get()` like firmware. Without it, or
  with a damaged one, the driver logs why and does not attach.
- `tools/airos/firmware/rtl8710b-tables.py` (MIT, holds no register data)
  makes that file from a Linux tree's `8710b.c`. The data file is
  distributed under the GPL-2.0 with `8710b.c` as its source.

## Table file format (version 1)

All little-endian; offsets from the start of the file. The authoritative
description is `dev/rtwn/rtl8710b/r10b_tables.h`.

| Offset | Size | Field |
|---|---|---|
| 0x00 | 8 | magic `RTWNTABL` |
| 0x08 | 2 | format version, 1 |
| 0x0a | 2 | header size, 128 |
| 0x0c | 4 | chip id `0x8710b` |
| 0x10 | 4 | file size |
| 0x14 | 4 | number of tables (1..16) |
| 0x18 | 4 | CRC-32 (zlib's) of the file with this field as zero |
| 0x1c | 4 | flags, 0 |
| 0x20 | 32 | SHA-256 of the source file (informational) |
| 0x40 | 64 | source description, ASCII, NUL padded |
| 0x80 | 16 × n | table directory |

Directory entry: `u16 kind` (1 MAC, 2 BB, 3 AGC, 4 RF path A), `u16
variant` (0 any, `0xee` QFN48M-U, `0xfe` QFN48M-S: the package byte at
physical eFuse offset 0xf8), `u32` reserved (0), `u32` entry count
(1..1024), `u32` offset of the entries. Entries are `u32 register, u32
value` pairs in write order, without the Linux arrays' end markers. RF
registers 0xf9..0xfe are delay codes (50 ms, 5 ms, 1 ms, 50 µs, 5 µs, 1 µs
from 0xfe down), not writes.

The reader (`r10b_tables.c`) checks magic, version, header size, chip id,
size, CRC, directory bounds, unique (kind, variant) pairs and every entry's
range (MAC: register < 0x800, value ≤ 0xff; BB/AGC: 0x800 ≤ register <
0x1000, 4-byte aligned; RF: register ≤ 0xff, value ≤ 0xfffff). For a
package it takes each kind's table for that package, else the one for any
package; all four kinds must resolve.

The file made from Linux v6.18 (`8710b.c` sha256 `577ac51f...6d03`; v6.12
and later have the same tables) is 7,288 bytes: MAC 97 entries, BB 223 per
package, AGC 130, RF 105 per package.

```
tools/airos/firmware/rtl8710b-tables.py linux/drivers/net/wireless/realtek/rtl8xxxu/8710b.c \
	-o rtwn-rtl8710b-tables.bin --source-desc "GPL-2.0-only; Linux v6.18 rtl8xxxu/8710b.c"
tools/airos/firmware/rtl8710b-tables.py .../8710b.c --check rtwn-rtl8710b-tables.bin
```

## Files the driver loads

All in `firmware/realtekwifi/` (system or non-packaged data directory):

| rtwn name | File | From |
|---|---|---|
| `rtwn-rtl8710bufw_SMIC` | `rtwn-rtl8710bufw_SMIC.ucode` | linux-firmware `rtlwifi/rtl8710bufw_SMIC.bin` (signature 0x10b1) |
| `rtwn-rtl8710bufw_UMC` | `rtwn-rtl8710bufw_UMC.ucode` | linux-firmware `rtlwifi/rtl8710bufw_UMC.bin` (0x10b2) |
| `rtwn-rtl8710b-tables` | `rtwn-rtl8710b-tables.bin` | the generator, from Linux `8710b.c` |
| `rtwn-rtl8188fufw` | `rtwn-rtl8188fufw.ucode` | linux-firmware `rtlwifi/rtl8188fufw.bin` (0x88f1) |

The firmware image is picked by the die's foundry (SYSON SYSTEM_CFG0
bits 7:6: 0 SMIC, 2 UMC); TSMC dies have no firmware and are refused, as
Linux does. HaikuPorts' `realtek_wifi_firmwares` (2019) has none of these
(nor `rtwn-rtl8723bufw.ucode` for the RTL8723BU branch).

## What is implemented

- USB attach for `0bda:b711` and `0bda:2005` (vendor-class interface 0).
- Register access: MAC registers below 0x100 at 0x8000 + address; the
  generic firmware loader's `R92C_MCUFWDL` accesses redirected to the
  RTL8710B's 8051 control register 0x90; rtwn's test-chip check answered
  from SYSON; firmware blocks in 4-byte transfers (`usb/r10bu_reg.c`).
- SYSON indirect register access and indirect eFuse reads; chip
  identification (cut, foundry, package type); eFuse map (MAC address, TX
  power per channel group, crystal capacitance, thermal meter, board
  options); a new optional rtwn hook `sc_efuse_read` for chips with their
  own eFuse access.
- Power on (card disabled → emulation → active, MAC blocks, CM4 suspend
  off) and power off (FIFO flush, low power, MCU reset, emulation).
- Firmware download (SMIC/UMC image, signature 0x10b), MCU reset.
- MAC/BB/AGC/RF init from the table file, RF_ENV handling, RF switch
  control, enable RF; burst/A-MPDU setup; RX aggregation off; statistics.
- LC calibration (the RTL8188F's) and IQ calibration (path A, RTL8710B
  sequence); crystal capacitance from the eFuse.
- Channel and 20/40 MHz switching with the channel 13/14 CCK filters; TX
  power as the RTL8188F.
- RX: RTL8188F descriptor parsing, RSSI from the newer ("Jaguar 2") PHY
  status; TX: RTL8812A-style 40-byte descriptor with an inverted checksum
  (a new `tx_csum_invert` flag in rtwn's USB layer).
- Rate control: net80211's (as for the RTL8188F).

## Not implemented / open

- No hardware test at all. Everything below "attach" is unverified.
- No CFO (crystal) tracking, no firmware rate adaptation, no power saving
  verification, no LED, no AP mode check, no Bluetooth (the chip has
  none).
- rtwn's `rtwn_init()` clears `R92C_GPIO_MUXCFG_ENBT` (here 0x8040), which
  Linux does not do for this chip.
- `page_size` is 128 like FreeBSD's RTL8188F/RTL8723B attachments, while
  the chip's TX page is 256 bytes (matters for firmware reserved pages).
- Linux writes `REG_HMTFR` = 0x0f after starting this firmware; rtwn (and
  FreeBSD's RTL8188F code) does not.

## Test plan (when an RTL8188GU dongle is available)

1. Install the firmware and table file in
   `/boot/system/non-packaged/data/firmware/realtekwifi/` and the branch's
   `realtekwifi` (from an image built from the branch, or the driver in
   `non-packaged/add-ons/kernel/drivers/bin` with the dongle unplugged:
   a copy there loads at once).
2. Plug the dongle. `listusb -v`: after `usb_modeswitch`, `0bda:b711` (or
   `2005`) with one vendor-class interface 0; if the interface number
   differs, the device table's interface index must change.
3. syslog: `RTL8710B (RTL8188GU), <foundry> die, cut X, ROM n, package
   QFN48M-U|S` and `register tables: MAC 97, BB 223, AGC 130, RF 105`; no
   `eFuse map id` error; `MAC/BB RTL8710B, RF 6052 1T1R`; the MAC address
   matches the dongle's label or Linux's.
4. Negative checks: remove or truncate the table file → attach refused with
   the message, no crash. Remove the firmware image → rtwn brings the
   interface up without firmware (as for every rtwn chip); record whether
   scanning works that way.
5. `ifconfig /dev/net/realtekwifi/0 up`, scan (`ifconfig ... scan`): APs on
   channels 1–13 with plausible signal levels; compare with Linux
   (`iw dev wlan0 scan`) in the same place.
6. Join WPA2 (`ifconfig ... join SSID PASS`), DHCP, ping the gateway for 10
   minutes, `iperf3` both ways; look for TX hangs (the checksum inversion)
   and firmware C2H/TX report messages with `rtwn` debug on.
7. Channel 13 and 14 (if the regulatory domain allows), HT40 with the
   `ht40` tunable, unplug/replug and `ifconfig down/up` cycles (power off
   path), suspend/resume if the machine supports it.
8. Compare with Linux `rtl8xxxu` on the same dongle: syslog of the probe
   (cut, vendor, package, firmware revision) and throughput.
